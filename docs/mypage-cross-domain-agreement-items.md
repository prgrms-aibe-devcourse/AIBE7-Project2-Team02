# 마이페이지 연계 교차 도메인 합의 항목

## 1. 재점검 결론

이 문서는 마이페이지 담당자가 독립적으로 고칠 수 없는 항목만 남긴다. 실제 코드와 테스트를 다시 확인한 결과, 이전 문서에는 이미 구현된 기능을 미구현처럼 표현하거나 현재 요구사항보다 먼 엣지 케이스를 필수 합의 사항으로 확대한 부분이 있었다.

담당자 확인 이후 항목 상태는 다음과 같이 갱신한다.

1. `Payment.COMPLETED`를 거래 완료로 볼지 여부는 아직 합의가 필요하다.
2. Proposal·Estimate 상태 전이와 활성 거래 탈퇴 판정은 담당자가 작업 중이다.
3. Estimate 식별자와 연결 규약은 아래 제시 방향에 따라 교정한다.
4. 종료된 채팅방의 읽기 전용 전환은 설정 완료로 전달받았으며, 병합 후 서버 쓰기 경로까지 차단되는지만 확인한다.

회원 탈퇴의 기본 정책인 "활성 거래가 있으면 탈퇴 불가"는 이미 구현되어 있다. 남은 문제는 정책 부재가 아니라 활성 거래 판정에 사용하는 원본 상태가 제대로 종료되지 않거나 일부 경로가 누락되는 정확성 문제다.

## 2. 이미 구현되어 합의 대상에서 제외한 항목

| 항목 | 확인된 구현 |
| --- | --- |
| 활성 거래가 있는 회원의 탈퇴 차단 | `AccountProfileService.withdraw()`가 `AccountTradeActivityPort.hasActiveTrade()`를 호출하고 활성 거래가 있으면 `ACTIVE_TRANSACTION_EXISTS`로 거부한다. 서비스와 MVC 테스트가 존재한다. |
| 계정 ID와 판매자 프로필 ID 구분 | JWT subject는 계정 ID로 사용하고 판매자 도메인 접근 시 `SellerApplicationRepository`를 통해 프로필 ID로 변환한다. |
| 견적 참여자 권한과 상태 변경 | Quote 조회·수정·수락·거절·철회에 참여자 및 발신자·상대방 검증이 적용되어 있다. |
| 확정 견적의 결제·정산 | `Quote.ACCEPTED → Payment.COMPLETED → Settlement` 흐름이 구현되어 있다. |
| 결제 중복 방지 | `payments.quote_id` 고유 제약, 견적 행 비관적 잠금, 동시 결제 통합 테스트가 구현되어 있다. 운영 DB 적용만 남았다. |
| 마이페이지 거래 집계 | JWT 계정 ID 기반 구매·판매 조회와 제안 기반 거래의 최신 Quote 축약이 구현되어 있다. |
| 외부 거래 응답의 참여자 ID 은닉 | 마이페이지 거래 응답은 구매자 계정 ID와 판매자 프로필 ID를 외부에 반환하지 않는다. |

## 3. 마이페이지 또는 현재 작업 범위에서 독립 처리 가능한 항목

다음 항목은 다른 도메인의 정책 합의가 선행되지 않아도 현재 계약 안에서 수정할 수 있으므로 교차 도메인 합의 대상에서 제외한다.

| 항목 | 처리 방향 |
| --- | --- |
| `PER_PERSON` 금액 표시 | `TradeActivityResponse`에 `budgetType`을 전달하거나 Estimate 금액 라벨을 "총액"이 아닌 "요청 예산"으로 표시한다. 기존 `BudgetType` 의미를 그대로 사용하면 된다. |
| 카드 라벨·색상·검색·필터 | 원본 상태를 변경하지 않는 범위에서 마이페이지 UI가 처리한다. |
| 키보드 이동·상세 링크 | 기존 리소스 ID와 URL 계약 안에서 마이페이지 JavaScript가 처리한다. |
| 서버 페이징 구현 방식 | 현재 집계 API의 후속 성능 작업이다. 외부 계약 변경 시에만 소비자와 조율하며, 별도 거래 원장 합의의 선행 조건은 아니다. |
| 결제 고유 제약 운영 반영 | 팀 정책 합의가 아니라 배포 절차다. 운영 담당자가 제공된 SQL을 실행하고 결과를 검증한다. |

## 4. 교차 도메인 합의 및 진행 상태

### 4.1 결제 완료와 거래 완료의 관계

**문제**

현재 마이페이지는 `Payment.COMPLETED`를 완료로 표시한다. 현재 프로젝트가 결제 성립까지만 주문 범위로 정의한다면 이 동작은 정상이며 별도 주문 이행 모델은 필요하지 않다. 준비·배송·서비스 제공 완료까지 추적해야 한다는 요구사항이 있을 때만 결제 완료와 거래 완료를 분리해야 한다.

**프로젝트 영향**

- 결제 완료를 최종 완료로 합의하면 현재 구조를 유지할 수 있다.
- 별도 이행 단계가 필요한데 현재 구조를 유지하면 결제 직후 진행 거래가 완료로 표시된다.
- 완료 정의는 마이페이지뿐 아니라 탈퇴 판정과 향후 정산 완료 시점에 영향을 준다.

**제시 가능한 방향성**

- 권장 1안: 현재 제출 범위가 결제까지라면 `Payment.COMPLETED = 거래 완료`로 명시하고 추가 주문 모델을 만들지 않는다.
- 선택 2안: 준비·배송 상태가 요구될 때만 `Quote` 기준 이행 레코드 또는 별도 주문 엔티티를 추가한다.
- 2안을 선택할 때도 공통 `tradeId`나 환불 원장을 선행 구현하지 말고 실제 요구되는 상태와 API부터 최소 범위로 설계한다.

**필요한 합의**

- 주문·결제 담당: 이번 프로젝트의 주문 완료 범위
- 계정 담당: 완료 상태가 탈퇴 차단에서 해제되는 시점
- 마이페이지 담당: 완료 탭으로 이동시키는 원본 상태

### 4.2 Proposal·Estimate 상태 전이

**진행 상태: 담당자 작업 중**

**문제**

`ProposalStatus`와 `EstimateStatus`에는 `IN_TALK`, `ACCEPTED`, `REJECTED`, `WITHDRAWN` 등이 정의되어 있지만 엔티티와 서비스에는 상태 변경 메서드가 없고 컨트롤러도 등록·조회만 제공한다. 생성된 Proposal은 `SENT`, Estimate는 `REQUESTED`에 머문다.

**프로젝트 영향**

- 마이페이지가 원본 요청의 실제 진행 상태를 표시할 수 없다.
- 판매자가 보낸 Proposal과 받은 Estimate가 종료 상태로 전이되지 않아 탈퇴가 계속 차단될 수 있다.
- 채팅과 Quote가 이미 진행되거나 확정돼도 원본 도메인에는 상태가 반영되지 않는다.

**제시 가능한 방향성**

- Proposal과 Estimate 담당자가 각 상태의 변경 주체와 허용 전이를 먼저 확정한다.
- 채팅 생성 시 `IN_TALK`, Quote 확정 시 `ACCEPTED`, 명시적 거절·철회 시 `REJECTED/WITHDRAWN`으로 변경한다.
- 상태 변경은 마이페이지가 아니라 각 도메인의 명령 서비스에서 처리한다.
- 하나의 주문 요청에 여러 제안을 허용하는 현재 구조에서는 선택되지 않은 제안을 자동 거절할지 여부만 별도로 결정한다.

**필요한 합의**

- Proposal·Estimate 담당: 상태 변경 API와 전이 규칙
- 채팅·Quote 담당: 전이를 발생시키는 시점과 호출 방식
- 계정 담당: 어떤 원본 상태를 활성 거래로 계산할지

작업 브랜치가 병합되면 상태 전이 API, 채팅·Quote 연동 시점, 종료 상태 처리를 코드와 통합 테스트로 확인한다. 별도 중복 구현은 하지 않는다.

### 4.3 Estimate의 식별자 의미와 Quote 연결

**진행 상태: 제시 방향에 따라 교정 예정**

**문제**

Estimate의 `requestId`는 이름과 달리 `OrderRequest.id`가 아니라 구매자 계정 ID를 저장한다. Proposal의 `requestId`는 실제 `OrderRequest.id`이므로 두 도메인의 같은 필드명이 서로 다른 의미를 가진다. Estimate에서 시작된 ChatRoom 또는 Quote를 직접 식별하는 필드도 없다.

**프로젝트 영향**

- 새 기능 작성자가 Estimate의 `requestId`를 주문 요청 ID로 오해할 수 있다.
- Estimate가 Quote로 발전해도 마이페이지에서 같은 거래임을 안전하게 판단할 수 없다.
- 주문·Estimate·Quote 담당자가 서로 다른 ID를 연결하면 조회 누락이나 권한 판정 오류가 발생할 수 있다.

**제시 가능한 방향성**

- 최소 수정안: Estimate의 현재 컬럼 의미를 `buyerAccountId`로 명시하고 DTO·서비스 명칭을 단계적으로 정리한다.
- Estimate가 Quote로 이어지는 요구가 있다면 ChatRoom에 `estimateId`를 선택적으로 추가하고 Quote는 기존 `chatRoomId` 연결을 사용한다.
- Estimate가 독립 요청으로 끝나는 기능이라면 Quote와 억지로 연결하지 않고 마이페이지에서도 별도 항목으로 유지한다.

**필요한 합의**

- Estimate 담당: Estimate가 Quote·채팅으로 발전하는 기능인지 여부
- 주문 담당: Estimate가 반드시 OrderRequest를 참조해야 하는지 여부
- 채팅·Quote 담당: 연결이 필요할 때 저장할 기준 ID

현재는 위 방향성을 구현 기준으로 사용한다. 교정 결과에서 Estimate가 독립 요청인지 Quote로 이어지는 요청인지 확정되면 해당하지 않는 선택지는 제거한다.

### 4.4 활성 거래 탈퇴 판정의 정확성

**진행 상태: 담당자 작업 중**

**문제**

활성 거래가 있으면 탈퇴를 막는 정책과 포트는 이미 구현되어 있다. 다만 현재 `JpaAccountTradeActivityAdapter` 판정에는 다음 문제가 있다.

- 구매자가 보낸 Estimate를 조회하지 않는다.
- Quote는 결제 완료 후에도 `ACCEPTED`이므로 완료 거래가 계속 활성으로 계산된다.
- QuoteNegotiation은 상태 조건 없이 존재 여부만 확인하므로 하위 거래가 종료된 뒤 남은 협상도 계속 활성으로 계산된다.
- Proposal과 Estimate에 종료 전이가 없어 생성 후 계속 활성으로 남을 수 있다.

`EstimateStatus.IN_TALK`가 활성 상태 집합에 없는 점은 현재 상태 변경 기능이 없어 당장 재현되는 결함은 아니다. Proposal·Estimate 상태 전이를 추가할 경우 함께 보정해야 하는 잠재 누락이다.

**프로젝트 영향**

- 일부 구매자는 진행 중인 Estimate가 있어도 탈퇴할 수 있다.
- 반대로 협상 잠금 또는 결제 완료 후에도 사용자가 계속 탈퇴하지 못할 수 있다.
- 현재 `AccountProfileServiceTest`는 포트를 mock하므로 실제 JPA 판정의 누락과 과차단을 검증하지 않는다.

**제시 가능한 방향성**

- 탈퇴 정책 자체는 유지하고 `JpaAccountTradeActivityAdapter`의 실제 쿼리와 활성 상태 집합만 보정한다.
- 구매자 Estimate 조회와 상태 조건이 있는 QuoteNegotiation 조회를 추가한다.
- `Payment.COMPLETED`를 최종 완료로 합의하면 완료 결제가 있는 `Quote.ACCEPTED`는 활성 거래에서 제외한다.
- Proposal·Estimate 상태 전이가 추가되면 종료 상태를 활성 집합에서 제외한다.
- H2 또는 PostgreSQL 통합 테스트로 구매자·판매자·완료·종료 경로를 검증한다.

**필요한 합의**

- 계정 담당: 기존 탈퇴 차단 정책 유지
- Proposal·Estimate·Quote 담당: 활성·종료 상태의 의미
- 결제 담당: 완료 결제가 활성 거래를 종료시키는지 여부

작업 브랜치가 병합되면 구매자 Estimate 누락, 완료 Quote·종료 협상 과차단, Proposal·Estimate 종료 상태 반영을 중심으로 회귀 검사한다. 별도 중복 구현은 하지 않는다.

### 4.5 종료된 채팅방의 쓰기 정책

**진행 상태: 읽기 전용 전환 설정 완료 전달, 병합 검증 대기**

**문제**

Quote가 `REJECTED` 또는 `WITHDRAWN`으로 변경되면 ChatRoom은 `CLOSED`가 된다. 담당자로부터 종료 시 필드가 읽기 전용으로 전환되도록 설정했다는 내용을 전달받았다. 다만 현재 `merge`의 메시지·파일 서비스는 참여자 여부만 검증하고 ChatRoom 상태를 확인하지 않으므로 해당 변경은 아직 병합본에서 확인되지 않는다.

**프로젝트 영향**

- UI는 종료 거래로 표시하지만 동일 채팅방에서 새 메시지나 파일이 생성될 수 있다.
- 이는 마이페이지 표시 문제가 아니라 ChatRoom의 `CLOSED` 의미가 읽기 전용인지 단순 표시인지 불명확한 문제다.

**제시 가능한 방향성**

- 담당자 변경이 병합되면 종료된 방에서 입력 필드가 비활성화되는지 확인한다.
- UI 설정과 별개로 메시지 발행과 파일 업로드 API가 `ACTIVE` 상태를 요구하는지 확인한다.
- 대화·파일 조회는 참여자에게 계속 허용해 읽기 전용 요구를 유지한다.

**완료 확인 조건**

- 종료된 방의 UI 입력 필드 비활성화
- WebSocket 메시지 발행과 파일 업로드 직접 호출 차단
- 기존 대화와 첨부파일 조회 유지

## 5. 현재 범위에서 제외한 미래 항목

다음 내용은 기능 요구가 확정되지 않은 상태에서 필수 문제처럼 다루지 않는다.

- 리뷰·신고 기능이 사용할 공통 `tradeId`
- 결제 완료 후 부분 환불과 환불 이력 원장
- 관리자 강제 취소와 분쟁 처리
- 대화·첨부파일 법적 보존 기간
- Flyway 또는 Liquibase 도입
- 실제 PG 웹훅과 외부 idempotency key
- 준비·배송·이행 상태를 포함하는 별도 주문 엔티티

실제 PG 연동이나 주문 이행 기능이 이번 프로젝트 범위로 확정될 때 별도 설계 문서에서 다룬다.

## 6. 후속 확인 순서

1. `Payment.COMPLETED`를 이번 범위의 최종 거래 완료로 볼지 결정
2. 작업 중인 Proposal·Estimate 상태 전이와 탈퇴 판정 변경 병합 후 회귀 검사
3. Estimate 식별자와 연결 규약 교정 결과 확인
4. 종료된 ChatRoom의 UI 및 서버 쓰기 차단 확인

## 7. 마이페이지 단독 처리 범위

위 합의와 병합 검증 이후 다음 작업은 마이페이지 담당자가 독립적으로 처리한다.

- 합의된 상태의 한글 라벨과 색상
- `PER_PERSON`과 `TOTAL` 금액 라벨 보정
- 검색·필터·정렬과 카드 레이아웃
- 빈 상태·오류 상태·재시도 UX
- 합의된 상세 URL로 이동

마이페이지는 상태 의미, 완료 시점, 원본 ID 관계, 탈퇴 가능 여부를 추정하거나 변경하지 않는다.
