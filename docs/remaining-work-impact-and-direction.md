## 3. 주문 도메인 판단

현재 주문 성립 파이프라인은 다음과 같다.

```text
Quote.ACCEPTED
  -> Payment.COMPLETED
  -> Settlement 발행
```

이는 거래 조건 확정, 구매자 결제, 판매자 정산 문서 생성까지 담당하므로 기본적인 거래 성립 기능은 존재한다.

다만 다음 기능은 현재 범위에 구현되어 있지 않다.

- 주문 준비 시작
- 배송 시작과 배송 완료
- 최종 거래 완료
- 주문 취소·환불
- 완료 후 탈퇴 제한 해제
- 주문 상태 변경 감사 이력

따라서 별도 `Order` 엔티티가 현재 즉시 필요하다고 단정하지 않는다. 이번 프로젝트가 결제 성립까지를 완료로 정의하면 현 구조를 유지한다. 준비·배송·이행 상태가 요구사항으로 확정될 때만 `Quote`를 기준으로 한 최소 이행 모델을 검토한다.

## 4. 권장 구현 순서

1. 운영 결제 고유 제약 적용
2. 결제 완료를 최종 거래 완료로 볼지 합의
3. Proposal·Estimate 상태 전이와 탈퇴 판정 정확성 보정
4. Estimate ID 의미 및 Quote 연결 필요 여부 결정
5. 거래 금액 표시와 서버 페이징 보강
6. 운영 데이터, CORS, OpenAPI 정책 정리
7. 확정된 요구사항에 따라 실제 PG 또는 주문 이행 기능 진행
8. 소셜 인증, 문의, 신고 기능을 별도 작업으로 진행

## 6. 즉시 확인할 운영 항목

```sql
SELECT quote_id, COUNT(*)
FROM payments
GROUP BY quote_id
HAVING COUNT(*) > 1;
```

위 조회 결과가 없어야 결제 고유 제약을 안전하게 추가할 수 있다. 중복이 있으면 레코드 상태, PG 거래번호, 정산서 연결을 확인해 보존할 결제를 결정한 뒤 마이그레이션을 실행한다.
