# 마이페이지 장기 최적화 리포트

## 1. 현재 결론

현재 구현은 기능과 보안 요구를 충족하며 소규모 운영에는 사용할 수 있다. 다만 목록 API가 일부 도메인에서 전체 데이터를 읽은 뒤 메모리에서 필터링·페이지 절단하고, 마이페이지가 첫 100건만 가져오는 구조이므로 데이터가 누적되면 응답 시간, DB 부하, 누락된 과거 내역 문제가 발생한다.

이 제한은 현재 PR의 배포 차단 사유는 아니지만 장기 운영 전 반드시 개선해야 한다.

## 2. 확인된 병목과 영향

| 우선도 | 문제 | 장기 영향 |
|---|---|---|
| P1 | 거래 활동이 제안·견적·결제·채팅 전체 목록을 읽은 뒤 합성한다 | 사용자별 데이터 증가에 비례해 쿼리량, 메모리, 정렬 시간이 증가한다 |
| P1 | 마이페이지가 각 출처의 첫 100건만 조회한다 | 100건을 넘은 과거 거래·채팅이 화면에서 조회되지 않는다 |
| P1 | 화면 상태 필터가 받은 데이터에만 적용된다 | 첫 페이지 밖의 동일 상태 데이터가 검색 결과에서 누락된다 |
| P2 | 제안·채팅 페이지 응답도 서비스 내부 전체 조회 후 절단한다 | API 형식은 페이징이지만 DB 부하는 줄지 않는다 |
| P2 | 인덱스 생성이 Hibernate `ddl-auto`에 의존한다 | 운영 환경에서 `ddl-auto`를 끄면 인덱스가 보장되지 않는다 |
| P2 | 15초/60초 재조회가 목록 전체를 다시 요청한다 | 활성 사용자가 증가하면 동일 데이터 반복 조회가 늘어난다 |
| P3 | 신고 처리 결과는 조회 API만 있고 사용자 알림함이 없다 | 사용자가 결과를 확인하려면 별도 화면 재방문이 필요하다 |

## 3. 목표 구조

1. 단일 테이블 목록은 Spring Data `Pageable`과 상태 조건을 저장소 쿼리에 직접 전달한다.
2. 거래 활동처럼 여러 도메인을 합치는 목록은 읽기 전용 `trade_activity` 프로젝션 또는 이벤트 기반 조회 테이블을 둔다.
3. 정렬 키는 `(occurred_at DESC, activity_id DESC)`로 고정하고 커서에 두 값을 함께 포함한다.
4. 화면은 `content`, `nextCursor`, `hasNext`를 받아 실제 다음 페이지를 요청한다.
5. 검색과 상태 필터 변경 시 커서를 초기화하고 서버에 조건을 전달한다.
6. 상태 변경은 전체 목록 재조회 대신 변경 버전 또는 `updatedSince` 기반 증분 조회를 사용한다.

## 4. 단계별 전환 계획

### 4.1 P1: 조회 누락 제거

1. 마이페이지 출처별 현재 페이지와 `hasNext`를 관리한다.
2. 더 보기 클릭 시 해당 출처의 다음 페이지를 요청하고 중복 ID를 제거해 병합한다.
3. 상태 필터와 검색어를 서버 요청에 전달한다.
4. 100건 상한을 제거하고 모든 내역에 도달할 수 있는 통합 테스트를 추가한다.

완료 기준: 101건 이상의 거래·채팅 데이터에서 첫 항목부터 마지막 항목까지 중복·누락 없이 조회된다.

### 4.2 P1: DB 페이징 전환

1. 제안 저장소를 판매자/주문자/상태/생성 시각 조건의 `Slice` 조회로 변경한다.
2. 채팅 저장소를 구매자 또는 판매자 참여 조건과 상태 조건의 커서 조회로 변경한다.
3. 최근 메시지는 채팅방 ID 묶음에 대한 단일 배치 쿼리를 유지한다.
4. 거래 활동은 조회 전용 프로젝션을 도입해 제안·견적·결제 상태 변경 시 갱신한다.

완료 기준: 페이지 크기와 무관하게 전체 엔티티를 먼저 읽는 쿼리가 실행 계획에서 제거된다.

### 4.3 P2: 운영 인덱스 보장

1. 채팅방, 제안, 견적 테이블 생성 이후 실행되는 버전형 Flyway 마이그레이션을 추가한다.
2. PostgreSQL 운영 환경에서는 필요 시 `CREATE INDEX CONCURRENTLY`를 별도 배포 단계로 실행한다.
3. 실제 조회 쿼리에 `EXPLAIN ANALYZE`를 수행해 인덱스 스캔과 정렬 비용을 확인한다.

완료 기준: 운영 스키마가 Hibernate 자동 갱신 없이도 필요한 인덱스를 보유한다.

### 4.4 P2: 상태 동기화 경량화

1. 목록 응답에 마지막 변경 버전 또는 최신 `updatedAt`을 포함한다.
2. 포커스 복귀와 주기 갱신은 `updatedSince` 이후 변경분만 요청한다.
3. 정지·탈퇴처럼 즉시 차단해야 하는 계정 상태는 현재 JWT 검증 방식을 유지한다.

완료 기준: 변경이 없는 주기 갱신에서 대형 목록 본문을 전송하지 않는다.

## 5. 권장 측정 항목

- 사용자별 거래 활동 100, 1,000, 10,000건에서 p50/p95 응답 시간
- 목록 요청당 SQL 수와 조회 행 수
- 응답 본문 크기와 서버 힙 사용량
- 더 보기 과정의 중복·누락 건수
- 상태 변경 후 화면 반영 지연
- 인덱스 적용 전후 실행 계획과 정렬 비용

## 6. 운영 전 권장 임계값

- p95 목록 응답 500ms 이하
- 페이지 크기 기본 20, 최대 100
- 목록 API 요청당 반환 행 100건 이하
- 동일 페이지 중복 ID 0건
- 전체 순회 누락 0건
- 변경 없는 상태 갱신 응답 본문 10KB 이하

## 7. 이번 PR에서 확정한 범위

이번 PR은 현재 API 호환성, 기능 완결성, 보안 경계, 제한적 페이지 계약, 상태 재조회까지 확정한다. DB 커서 페이징, 거래 활동 프로젝션, 증분 동기화, 신고 결과 알림함은 후속 성능 개선 작업으로 분리한다.
