# 마이페이지 교차 도메인 수정 합의 STAR

## Situation | 상황

마이페이지의 구매·판매·채팅 조회를 여러 도메인과 연결하는 과정에서 완료 상태, 활성 거래 판정, Estimate 식별자, 종료 채팅방의 쓰기 정책을 서로 다르게 해석할 가능성이 확인됐다. 활성 거래가 있으면 탈퇴를 차단하는 기본 정책과 결제·정산 흐름은 이미 구현되어 있었으므로, 신규 기능 추가보다 기존 상태를 정확히 연결하고 중복 작업을 피하는 것이 필요했다.

1. 결제 완료와 거래 완료의 기준이 분리되어야 하는지 해석이 달랐다.
2. Proposal·Estimate 상태 전이와 탈퇴 판정에서 누락·과차단 가능성이 있었다.
3. Estimate의 `requestId`가 실제로는 구매자 계정 ID를 의미해 이름과 값의 의미가 달랐다.
4. 종료된 채팅방의 읽기 전용 정책이 UI와 서버 쓰기 경로에 동일하게 적용되는지 확인이 필요했다.

## Task | 과제

진행 거래의 누락과 완료 거래의 과차단을 방지하면서 마이페이지가 원본 도메인의 상태를 임의로 변경하지 않도록 해야 했다. 동시에 현재 구현 범위와 미래 확장 범위를 분리하고, 다른 담당자가 작업 중인 기능을 중복 구현하지 않는 협업 기준을 정해야 했다.

1. 현재 거래 완료 기준을 확정하고 변경 조건을 제한한다.
2. 원본 상태 전이와 활성 거래 판정이 같은 생명주기를 사용하도록 한다.
3. Estimate 식별자의 실제 의미와 후속 연결 규약을 명확히 한다.
4. 종료 채팅방은 조회만 허용하고 모든 쓰기 경로를 차단한다.

## Action | 행동

현재는 `Payment.COMPLETED`를 거래 완료로 유지하고 준비·배송 등 이행 단계가 추가될 때만 완료 기준을 변경하기로 했다. Proposal·Estimate 상태 전이와 탈퇴 판정 보정은 담당자 작업을 기다린 뒤 회귀 검사하며, Estimate 식별자는 실제 의미가 드러나도록 교정한다. 종료된 채팅방은 읽기 전용으로 유지하고 UI 비활성화뿐 아니라 메시지와 파일 쓰기 요청도 서버에서 차단되는지 확인한다.

1. `Payment.COMPLETED`를 현행 거래 완료 기준으로 유지하고, 이행 단계가 추가될 때만 재설계한다.
2. 담당자가 작업 중인 Proposal·Estimate 상태 전이와 탈퇴 판정은 중복 구현하지 않고 병합 후 회귀 검사한다.
3. Estimate 식별자는 구매자 계정 ID라는 의미가 드러나도록 교정하고, Quote 연결이 필요할 때만 별도 연결 ID를 추가한다.
4. `CLOSED` 채팅방은 UI 입력 비활성화와 함께 메시지 전송·파일 업로드 API에서도 쓰기를 거부하도록 확인한다.

## Result | 결과·배움

이미 구현된 정책, 진행 중인 작업, 현재 수정 대상, 미래 기능의 경계가 명확해져 중복 구현과 불필요한 설계 확장을 줄였다. 후속 병합에서는 상태 전이, 탈퇴 판정, 식별자 연결, 종료 채팅방 쓰기 차단만 회귀 검사하면 된다. 다음 프로젝트에서는 완료 기준과 상태 소유권을 먼저 합의하고, UI 제어가 아닌 서버 검증과 통합 테스트로 도메인 간 정책을 고정한다.

1. 거래 완료 기준을 현행 유지로 확정해 불필요한 주문 이행 모델 도입을 미뤘다.
2. 상태 전이와 탈퇴 판정의 담당 작업을 존중하면서 병합 후 검증 범위를 명확히 했다.
3. 식별자 의미를 이름과 일치시키는 규칙을 정해 향후 권한·조회 오류 가능성을 줄였다.
4. 읽기 전용 정책은 화면 제어만으로 완성되지 않으며 서버 불변 조건과 통합 테스트가 필요하다는 기준을 남겼다.
