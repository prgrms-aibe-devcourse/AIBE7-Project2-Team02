# MatchEAT 로그인·회원가입 모듈 작업 명세서

> 보관 상태: 이 문서는 초기 독립 모듈 설계 기록이다. 현재 운영 구현의 단일 원본은
> `src/main/java/org/example/matcheat/domain/account`이며, 아래의 모듈 통합 지침은 적용하지 않는다.
> `modules/login-account-management`는 루트 Gradle 빌드에 포함하거나 의존성으로 연결하지 않는다.

## 1. 문서 목적

이 문서는 다른 작업자 또는 에이전트가 MatchEAT의 로그인·회원가입 기능을 독립적으로 구현하고, 이후 메인 애플리케이션에 안전하게 통합할 수 있도록 작성한 실행 명세다.

이 문서 작성 당시에는 `modules/login-account-management`를 단일 원본으로 계획했다. 현재는 루트 계정 도메인으로 통합이 완료됐으므로 이 원칙과 Gradle project dependency 지침은 폐기됐다.

## 4. 변경 안전 규칙

1. 기본 작업 중 메인 프로젝트의 `build.gradle`, `settings.gradle`, `application.yaml`을 직접 수정하지 않는다.
2. 필요한 변경은 `integration/*.snippet` 또는 `*.example.yaml`로 제공한다.
3. 보안상 필요한 루트 `.gitignore` 보완은 허용하되 기존 규칙을 삭제하거나 재정렬하지 않는다.
4. 사용자 또는 다른 작업자가 만든 변경을 되돌리지 않는다.
5. 실제 비밀키, DB 비밀번호, 관리자 비밀번호를 코드·YAML·문서·테스트에 기록하지 않는다.
6. `.env` 내용을 로그나 최종 보고에 출력하지 않는다.
7. JJWT 기반 커스텀 필터를 복사하지 않는다. Spring Security의 Resource Server와 Nimbus JWT 지원을 우선 사용한다.
8. 전역 `SecurityFilterChain`을 모듈에서 강제로 등록하지 않는다. 통합용 설정 스니펫과 JWT 관련 Bean을 제공한다.
9. 모듈 내부 구현 타입을 다른 도메인에서 직접 참조하지 않도록 공개 API와 포트를 분리한다.

```text

```

```text
UserCredentialRepository

AccessTokenIssuer
```

확장용 포트는 다음 이름 또는 동등한 책임으로 제공할 수 있다.

```text
CurrentUserQuery

WithdrawAccountUseCase
SellerApplicationUseCase
AdminAccountManagementUseCase
SellerApprovalUseCase
```

Application 계층은 JPA, Servlet, Spring Security, Nimbus 타입에 직접 의존하지 않는다. Controller는 요청 DTO를 유스케이스 입력 모델로 변환하고, persistence/security adapter가 프레임워크 타입을 처리한다.

## 7. 회원 엔티티 규격

### 7.1 users

| 컬럼 | 권장 타입 | 제약 및 의미 |
|---|---|---|
| `user_id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | PK |
| `email` | `VARCHAR(254)` | 정규화 후 저장, UNIQUE, NOT NULL |
| `password_hash` | `VARCHAR(255)` | 현재 이메일 가입에서는 필수, 향후 소셜 전용 계정을 위해 DB nullable 허용 |
| `name` | `VARCHAR(50)` | NOT NULL |
| `role` | `VARCHAR(20)` | `USER`, `ADMIN` |
| `status` | `VARCHAR(20)` | `ACTIVE`, `SUSPENDED`, `WITHDRAWN` |
| `token_version` | `INTEGER` | NOT NULL, 기본값 0, 향후 일괄 토큰 무효화 연결점 |
| `created_at` | `TIMESTAMPTZ` | NOT NULL |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL |
| `withdrawn_at` | `TIMESTAMPTZ` | nullable |

규칙:

- JPA enum은 반드시 `EnumType.STRING`으로 저장한다.
- 회원가입 API는 `role`, `status`, `tokenVersion`을 입력받지 않는다.
- 가입 기본값은 `USER`, `ACTIVE`, `0`이다.
- 이메일은 `trim()` 후 `Locale.ROOT` 기준 소문자로 변환해 저장·조회한다.
- 이메일 중복은 사전 조회와 DB UNIQUE 제약을 모두 사용한다.
- 비밀번호 원문은 엔티티의 장기 상태로 유지하거나 로그에 출력하지 않는다.
- 엔티티를 API 응답으로 직접 직렬화하지 않는다.
- 무분별한 public setter 대신 생성 메서드와 상태 변경 메서드를 사용한다.

### 7.2 seller_profiles

| 컬럼 | 권장 타입 | 제약 및 의미 |
|---|---|---|
| `seller_id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | PK |
| `user_id` | `BIGINT` | `users.user_id` FK, UNIQUE |
| `business_name` | `VARCHAR(100)` | NOT NULL |
| `business_number` | `VARCHAR(20)` | 정규화 후 UNIQUE, NOT NULL |
| `latitude` | `DECIMAL(10,7)` | nullable |
| `longitude` | `DECIMAL(10,7)` | nullable |
| `delivery_radius_km` | `DECIMAL(8,2)` | nullable 또는 0 이상 |
| `verification_status` | `VARCHAR(20)` | `PENDING`, `APPROVED`, `REJECTED` |
| `rejection_reason` | `VARCHAR(500)` | nullable |
| `applied_at` | `TIMESTAMPTZ` | NOT NULL |
| `reviewed_at` | `TIMESTAMPTZ` | nullable |
| `reviewed_by` | `BIGINT` | 관리자 `users.user_id` FK, nullable |
| `version` | `BIGINT` | JPA `@Version` 낙관적 잠금 |

판매자 여부는 `users.role`을 `SELLER`로 변경해 표현하지 않는다. `users.role=USER`이면서 `seller_profiles.verification_status=APPROVED`인 경우 판매 기능을 허용한다.

## 8. 비밀번호 정책

- 길이: 8~64자
- ASCII 영문자 최소 1자
- 숫자 최소 1자
- 특수문자는 필수가 아니지만 입력을 허용한다.
- 비밀번호에는 자동 `trim()`을 적용하지 않는다.
- 제어문자는 거부한다.
- BCrypt strength 10을 기본값으로 사용한다.
- 저장 형식은 `{bcrypt}$2a$10$...`처럼 알고리즘 식별자를 포함한다.
- `DelegatingPasswordEncoder`를 사용해 향후 Argon2 매핑과 로그인 시 점진적 재해시가 가능하게 한다.
- 이번 범위에서는 BouncyCastle과 Argon2 의존성을 추가하지 않는다.

## 9. JWT 규격

### 9.1 기본 정책

- 알고리즘: HS256만 허용
- 토큰 종류: Access Token만 구현
- 기본 만료시간: 1시간
- 전달: `Authorization: Bearer <token>`
- 저장: 브라우저 `sessionStorage`
- 인증 쿠키는 생성·조회하지 않는다.
- 서버 세션은 생성하지 않는다.
- Refresh Token과 서버 토큰 저장소는 만들지 않는다.
- 로그아웃은 클라이언트가 토큰을 제거하는 동작으로 정의한다.

### 9.2 필수 Claim

| Claim | 값 |
|---|---|
| `sub` | `user_id` 문자열 |
| `iss` | 설정된 issuer |
| `aud` | 설정된 audience |
| `iat` | 발급 시각 |
| `exp` | 만료 시각 |
| `jti` | 토큰별 UUID |
| `role` | `USER` 또는 `ADMIN` |

이메일, 비밀번호 해시, 사업자 정보는 JWT에 넣지 않는다. `token_version`은 필드와 확장 지점만 준비하며 이번 Access Token 검증에서 DB 조회를 강제하지 않는다. 회원 상태 변경은 최장 Access Token 만료시간 이후 완전히 반영될 수 있음을 문서화한다.

### 9.3 구현 기술

- `spring-boot-starter-oauth2-resource-server`를 사용한다.
- 발급은 `NimbusJwtEncoder`, 검증은 `NimbusJwtDecoder`를 우선 사용한다.
- Base64로 저장한 최소 256비트 난수 비밀키를 명시적으로 디코딩한다.
- 키가 없거나 길이가 부족하면 애플리케이션 시작 단계에서 명확히 실패시킨다.
- Decoder는 HS256, issuer, audience, 만료시각을 검증한다.
- 직접 만든 `OncePerRequestFilter`로 Bearer 문자열을 파싱하지 않는다.
- JWT 예외나 원문 토큰을 콘솔에 출력하지 않는다.

## 10. API 계약

기본 prefix는 `/api/v1`이다.

### 10.1 이메일 중복 확인

```http
GET /api/v1/auth/email-availability?email=user@example.com
```

성공 `200 OK`:

```json
{
  "email": "user@example.com",
  "available": true
}
```

형식 오류는 `400 INVALID_EMAIL`을 반환한다. 이 API는 사용자 편의 기능이며 회원가입 트랜잭션의 UNIQUE 제약을 대체하지 않는다.

### 10.2 회원가입

```http
POST /api/v1/auth/signup
Content-Type: application/json
```

```json
{
  "email": "user@example.com",
  "password": "password1234",
  "passwordConfirm": "password1234",
  "name": "홍길동"
}
```

성공 `201 Created`:

```json
{
  "userId": 1,
  "email": "user@example.com",
  "name": "홍길동",
  "role": "USER",
  "status": "ACTIVE"
}
```

오류:

- `400 VALIDATION_FAILED`
- `400 PASSWORD_CONFIRM_MISMATCH`
- `409 EMAIL_ALREADY_EXISTS`

회원가입 성공 시 JWT를 자동 발급하지 않는다. 화면은 로그인 페이지로 이동한다.

### 10.3 로그인

```http
POST /api/v1/auth/login
Content-Type: application/json
```

```json
{
  "email": "user@example.com",
  "password": "password1234"
}
```

성공 `200 OK`:

```json
{
  "accessToken": "eyJ...",
  "tokenType": "Bearer",
  "expiresIn": 3600,
  "user": {
    "userId": 1,
    "email": "user@example.com",
    "name": "홍길동",
    "role": "USER"
  }
}
```

오류:

- 존재하지 않는 이메일과 틀린 비밀번호는 모두 `401 INVALID_CREDENTIALS`로 통일한다.
- 올바른 비밀번호지만 정지 회원이면 `403 ACCOUNT_SUSPENDED`를 반환한다.
- 탈퇴 회원이면 `403 ACCOUNT_WITHDRAWN`을 반환한다.
- 실패 응답에 비밀번호, 해시, 내부 예외 메시지를 포함하지 않는다.

### 10.4 공통 오류 형식

```json
{
  "timestamp": "2026-08-25T00:00:00Z",
  "status": 400,
  "code": "VALIDATION_FAILED",
  "message": "입력값을 확인해 주세요.",
  "path": "/api/v1/auth/signup",
  "fieldErrors": {
    "email": "올바른 이메일 형식이 아닙니다."
  }
}
```

필드 오류가 없으면 `fieldErrors`는 빈 객체 또는 생략 중 하나로 일관되게 처리한다.

## 11. 화면과 JavaScript

### 11.1 페이지

- `GET /login`: `templates/account/login.html`
- `GET /signup`: `templates/account/signup.html`
- 전체 index와 최종 디자인은 다른 작업자와 조율 대상이다.
- 이번 구현에서는 동작 검증이 가능한 최소 목업으로 작성해도 된다.
- CSS 클래스는 `account-` prefix를 사용해 전역 충돌을 줄인다.
- JavaScript는 HTML 인라인이 아니라 `static/account/js` 아래 파일로 분리한다.

### 11.2 sessionStorage

- 키 이름: `matcheat.accessToken`
- 로그인 성공 시 Access Token만 저장한다.
- 비밀번호와 비밀번호 확인값은 저장하지 않는다.
- 로그아웃 함수는 해당 키만 제거하고 다른 storage 값을 `clear()`하지 않는다.
- 인증 API 요청용 `authFetch` 또는 동등한 헬퍼를 제공한다.
- 헬퍼는 토큰이 있을 때만 `Authorization: Bearer ...`를 추가한다.
- 보호 API가 `401`을 반환하면 토큰을 제거하고 로그인 화면 연결점을 제공한다.

### 11.3 페이지 접근 정책

- HTML 페이지 자체는 Bearer 헤더 없이 접근 가능하게 둔다.
- 인증·인가의 최종 강제 지점은 `/api/**`다.
- `/api/v1/auth/signup`, `/api/v1/auth/login`, `/api/v1/auth/email-availability`는 공개한다.
- 향후 `/api/v1/account/me`는 인증을 요구한다.
- 향후 `/api/v1/admin/**`는 `ADMIN` 권한을 요구한다.
- 인증 쿠키를 사용하지 않는 동일 출처 API 기준으로 CSRF를 비활성화한다.
- 현재 동일 출처 구성이므로 광범위한 CORS 허용을 추가하지 않는다.

규칙:

- 기본값은 비활성화다.
- 활성화됐더라도 세 값이 모두 유효할 때만 생성한다.
- 관리자 이메일도 일반 이메일 규칙을 적용한다. 권장 로컬 형식은 `admin@matcheat.local`이다.
- 관리자 비밀번호를 코드나 example 파일에 기본값으로 넣지 않는다.
- 같은 이메일 또는 기존 ADMIN이 있으면 새로 만들지 않는다.
- 애플리케이션 재시작 시 기존 비밀번호를 덮어쓰지 않는다.
- 공개 회원가입 요청으로 ADMIN을 생성할 수 없어야 한다.
- 생성 성공 여부만 기록하고 비밀번호나 해시는 로그에 남기지 않는다.

## 13. 설정 파일 규격

프로필 기반 `.env` 로딩을 사용한다. `spring.profiles.active`는 프로필을 활성화하고, 활성화된 local 문서의 `spring.config.import`가 `.env`를 읽는다는 설명 주석을 example YAML에 작성한다.

예시:

```yaml
spring:
  application:
    name: MatchEAT
  profiles:
    active: local,db,account

---
spring:
  config:
    activate:
      on-profile: local
    import: optional:file:.env[.properties]
```

Account 설정:

```yaml
app:
  account:
    password-encoder: bcrypt
    jwt:
      secret: ${JWT_SECRET}
      issuer: ${JWT_ISSUER:https://matcheat.local}
      audience: ${JWT_AUDIENCE:matcheat-api}
      access-token-ttl: ${JWT_ACCESS_TOKEN_TTL:PT1H}
    admin-bootstrap:
      enabled: ${ADMIN_BOOTSTRAP_ENABLED:false}
      email: ${ADMIN_EMAIL:}
      password: ${ADMIN_PASSWORD:}
      name: ${ADMIN_NAME:}
```

DB 설정 example은 `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`를 사용한다. JWT secret과 DB password에는 작동 가능한 기본값을 제공하지 않는다.

루트 `.gitignore` 필수 규칙:

```gitignore
.env
.env.*
!.env.example
!.env.*.example
```

이미 추적된 `.env`는 ignore 추가만으로 제거되지 않으므로 `git ls-files`로 추적 여부를 확인한다. 파일 삭제나 인덱스 변경이 필요하면 사용자 승인 없이 파괴적 Git 작업을 하지 않는다.

## 14. Gradle 규격

독립 모듈은 메인 프로젝트의 Java 17, Spring Boot 4.1.1과 호환되어야 한다. 다음 기능에 필요한 최소 의존성만 포함한다.

- Spring Web MVC
- Spring Validation
- Spring Security
- Spring OAuth2 Resource Server
- Spring Data JPA
- Thymeleaf
- PostgreSQL runtime driver
- Lombok은 선택 가능
- Spring Security test 및 Web MVC test

제외 의존성:

- Redis

- BouncyCastle
- MySQL driver
- OAuth2 Client

메인 프로젝트 통합용 `settings.gradle`과 `build.gradle` 변경은 snippet으로만 제공한다. 통합 전 독립 테스트 명령과 통합 후 전체 테스트 명령을 `INTEGRATION.md`에 작성한다.

## 15. DB 스키마 관리

- `integration/auth-schema.sql`에 PostgreSQL 기준 생성 SQL과 제약을 제공한다.
- Flyway 사용을 권고하되 팀 전체 합의 전 모듈이 메인 DB에 자동 적용하지 않는다.
- 메인 프로젝트에서 Flyway를 채택하면 이 SQL을 중앙 migration 번호 규칙에 맞춰 이동한다.
- Hibernate `ddl-auto=update`를 모듈 설정에 강제하지 않는다.
- 최종 권장 운영값은 `ddl-auto=validate`다.
- 팀이 임시로 `update`를 사용하더라도 규격의 기준은 `auth-schema.sql`이다.

## 16. 테스트 요구사항

최소 테스트:

1. 정상 회원가입
2. 이메일 정규화
3. 이메일 중복 가입 거부
4. 잘못된 이메일 형식 거부
5. 비밀번호 길이·영문·숫자 정책
6. 비밀번호 확인 불일치
7. 비밀번호가 BCrypt 식별자 형식으로 저장됨
8. 정상 로그인과 JWT Claim 검증
9. 존재하지 않는 이메일과 잘못된 비밀번호가 같은 오류 코드 사용
10. 정지·탈퇴 회원 로그인 거부
11. 변조·만료·잘못된 issuer/audience JWT 거부
12. 공개 API는 토큰 없이 접근 가능
13. 보호 API는 토큰 없이 `401`
14. 일반 사용자의 관리자 API 접근은 `403`
15. API 응답에 비밀번호 원문과 해시가 노출되지 않음
16. 관리자 bootstrap의 비활성·최초 생성·재실행 멱등성

단순 `contextLoads()`만으로 완료 처리하지 않는다. 외부 PostgreSQL이 없어도 핵심 application/security 로직 테스트가 가능하도록 포트를 fake 또는 mock으로 대체한다. PostgreSQL 제약 통합 테스트는 환경이 허용할 때 별도 수행한다.

## 17. 참고 프로젝트에서 채택·배제할 요소

채택:

- profile별 YAML 분리
- `@ConfigurationProperties`와 `Duration`
- Controller → Service/Application → Repository 구조
- `DelegatingPasswordEncoder`
- stateless 보안 설정
- JavaScript `fetch` 로그인 흐름
- JPA auditing 개념

배제 또는 수정:

- 쿠키와 Bearer 동시 사용
- 응답 본문과 쿠키에 토큰 중복 전달
- 직접 구현한 Bearer 문자열 추출 필터
- 모든 사용자 권한을 `ROLE_USER`로 고정
- 변경 가능한 username을 JWT subject로 사용
- raw secret 문자열에 단순 `getBytes()` 적용
- `printStackTrace()`로 인증 오류 출력
- Redis 기반 미완성 Refresh Token
- MySQL과 `ddl-auto=update`
- `Optional<Object>` repository 반환
- 실제 값이 든 `.env` 추적

## 18. 현재 격리 절차

1. 운영 계정·로그인 변경은 루트 `domain/account`에서만 수행한다.
2. 이 모듈은 과거 구현을 확인할 때만 `-p modules/login-account-management`로 독립 실행한다.
3. 루트 `settings.gradle`, `build.gradle`, `SecurityConfig`에 이 모듈의 설정이나 Bean을 연결하지 않는다.
4. 과거 Gradle 및 보안 스니펫은 비활성 상태를 유지한다.
5. 운영 회귀 여부는 루트 계정·Security 테스트와 전체 프로젝트 테스트로 판정한다.

## 19. 완료 기준

- 필수 API와 두 목업 페이지가 명세대로 동작한다.
- 로그인 성공 토큰으로 보호 API 인증이 가능하다.
- 쿠키와 서버 세션을 사용하지 않는다.
- `.env`와 비밀값이 Git 추적 대상이 아니다.
- 코드 단일 원본 원칙을 지킨다.
- 모듈 테스트가 통과한다.
- 통합 스니펫과 인수인계 문서가 있다.
- 제외 범위를 임의로 구현해 의존성을 늘리지 않는다.
- 미실행 테스트나 미확정 통합 항목은 최종 보고에 명시한다.

## 20. 유일한 후속 팀 결정

Flyway를 프로젝트 전체 표준으로 사용할지는 팀 합의가 필요하다. 이 결정 전에도 엔티티, API, 테스트, `auth-schema.sql` 작성은 진행할 수 있다. 구현 에이전트는 Flyway를 메인 프로젝트에 자동 적용하지 말고 권고 및 통합 선택지로 남긴다.
